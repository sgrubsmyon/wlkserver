## Conventions

- **Append-only bookkeeping.** `verkauf`, `verkauf_mwst`, `verkauf_details`,
  `kassenstand`, `gutschein`, `anzahlung` and the settlements are never
  updated or deleted through the API. Corrections are new rows: a storno is a
  receipt with negated amounts that points at the original via
  `verkauf.storno_von`; a voucher redemption appends a row with the reduced
  balance; a settlement is immutable once written.
- **Article versioning.** Editing price-relevant fields inserts a new `artikel`
  row and sets `aktiv = FALSE` on the old one; positions keep referencing the
  old `artikel_id`. Deletion means deactivation.
- **Money** is `DECIMAL(13,2)` in euros, VAT rates are `DECIMAL(6,5)` fractions
  (0.19000 = 19 %). Timestamps are UTC `TIMESTAMP` columns; the API sets the
  session time zone to `+00:00`.
- **Special articles** are identified by `artikel_nr`, not by id:
  `RABATT1`/`RABATT2` (manual and receipt discount), `ANPASSUNG` (manual price
  change), `ANZAHLUNG`/`ANZAHLAUFLOES` (down payment and resolution),
  `GUTSCHEIN`/`GUTSCHEINEINLOES` (voucher sale and redemption), `PFAND*`
  (deposit articles).
- **Training.** The sandbox uses a separate database (`TRAINING_DB_URL`,
  normally `kasse_training`) with the same schema; production rows are never
  touched. Training TSE transactions carry `training = TRUE`.
- **Charset/collation** `utf8`/`utf8_general_ci`, storage engine InnoDB (the
  Java POS relies on it).
